# Study Space --- 개발용 통합 프롬프트

아래 프롬프트를 AI 코딩 도구(Cursor, Claude Code, Codex 등)에 제공해
Study Space 웹 애플리케이션을 구현한다. 먼저 프로젝트 구조와 현재 구현
상태를 확인하고, 기존 코드가 있다면 이를 존중하면서 단계적으로 구현한다.
한 번에 모든 기능을 무리하게 생성하기보다, 작동 가능한 MVP를 우선
완성한다.

------------------------------------------------------------------------

## 역할과 목표

너는 제품 기획, UX/UI, 프론트엔드, 백엔드, 데이터베이스 설계를 함께
수행하는 시니어 풀스택 엔지니어다.

대학생이 개인 학습을 관리할 수 있는 PC 중심 웹 애플리케이션 **Study
Space**를 구현한다. 이 서비스는 과목별 TODO, 카테고리, 과목별·전체 공부
타이머, 캘린더, 대시보드를 하나로 연결한다.

핵심 사용자 흐름은 다음과 같다.

1.  사용자가 로그인한다.
2.  수강 과목을 생성한다.
3.  과목별 카테고리와 TODO를 등록한다.
4.  TODO의 마감일이 캘린더에 표시된다.
5.  사용자는 과목 또는 TODO를 선택해 공부 타이머를 시작한다.
6.  공부 기록이 과목별 시간과 전체 시간에 함께 반영된다.
7.  대시보드에서 오늘 할 일, 완료율, 공부 시간 및 과목별 현황을
    확인한다.
8.  새로고침하거나 다시 로그인해도 데이터가 유지된다.

## 제품 및 기술 방향

-   플랫폼: PC 중심의 웹사이트. 주요 화면은 데스크톱에서 우선 설계하되
    태블릿과 모바일에서도 기본적인 사용이 가능하도록 반응형으로
    구성한다.
-   데이터: 로그인 기반 클라우드 저장. 사용자별 데이터가 분리되어야
    한다.
-   디자인: 카드형 대시보드 레퍼런스를 활용하되, 과도한 장식보다
    Toss에서 연상되는 명료하고 단정한 금융·생산성 서비스 UI를 지향한다.
-   폰트: Pretendard를 우선 사용한다.
-   그림자: 불필요한 drop shadow, 강한 글로우, 과도한 그라데이션을
    지양한다. 구분은 여백, 얇은 테두리, 배경색 차이로 해결한다.
-   우선순위: 핵심 기능의 정확성, 정보 구조, 접근성, 일관된 컴포넌트,
    안정적인 데이터 처리 순이다.

권장 스택(프로젝트에 기존 스택이 있다면 먼저 검토하고 불필요하게
교체하지 않는다): - Next.js + TypeScript - Tailwind CSS - shadcn/ui 또는
동등한 접근성 있는 컴포넌트 - Supabase Auth + PostgreSQL + Row Level
Security - Vercel 배포

## 주요 화면 및 기능

### 1. 인증

-   회원가입, 로그인, 로그아웃을 제공한다.
-   로그인 상태를 유지한다.
-   인증되지 않은 사용자는 개인 데이터 화면에 접근할 수 없도록 한다.
-   비밀 키와 service role key를 클라이언트에 노출하지 않는다.
-   Supabase를 사용하는 경우 모든 사용자 소유 데이터 테이블에 RLS 정책을
    설정한다.

### 2. Home --- 대시보드

-   오늘 완료한 TODO 수 / 오늘 예정된 TODO 수
-   오늘 공부 시간과 사용자가 설정한 일일 목표
-   오늘의 TODO 목록
-   마감 임박 및 기한이 지난 미완료 TODO 표시
-   과목별 TODO 완료 진행률
-   과목별 이번 주 공부 시간
-   빠른 TODO 추가 진입점
-   카드에는 실제 DB 데이터 또는 명확한 빈 상태를 표시한다. 샘플 숫자를
    실제 데이터처럼 하드코딩하지 않는다.

정의: - TODO 완료율은 TODO 상태를 기준으로 계산한다. - 공부 시간은 공부
세션 기록을 기준으로 계산한다. - "오늘"과 주간 통계는 사용자의 설정
시간대를 기준으로 계산한다.

### 3. Subjects --- 과목 관리

-   과목 생성, 수정, 보관, 삭제
-   과목명, 선택적 설명, 색상, 주간 목표 공부 시간
-   과목별 카테고리 생성·수정·삭제·정렬
-   과목별 TODO 목록
-   과목별 완료/미완료 개수 및 공부 시간
-   과목 삭제 시 관련 TODO, 카테고리, 일정, 공부 기록의 처리 정책을
    사용자에게 명확히 알린다. 파괴적 작업은 확인 절차를 제공한다.
-   삭제 대신 보관을 기본적인 비활성화 방법으로 제공하는 것을 권장한다.

### 4. Categories --- 카테고리

-   카테고리는 반드시 특정 과목에 속한다.
-   예: 운영체제 \> 과제 / 시험 공부 / 강의 복습
-   동일한 이름의 카테고리라도 과목이 다르면 별도 데이터다.
-   TODO가 연결된 카테고리를 삭제할 때는 TODO를 미분류로 옮길지, 다른
    카테고리로 옮길지 명확하게 처리한다.
-   TODO의 subject_id와 category의 subject_id가 일치하도록 검증한다.

### 5. TODO

각 TODO는 다음 정보를 가질 수 있다. - 제목(필수) - 과목(필수) -
카테고리(선택) - 상태: 미완료 / 완료 - 우선순위: 높음 / 보통 / 낮음 -
마감일(선택) - 예상 소요 시간(분, 선택) - 메모(선택) - 생성 시각, 수정
시각, 완료 시각

기능: - 생성, 상세 조회, 수정, 완료, 완료 취소, 삭제 - 미완료 우선
표시 - 기본 정렬은 마감일이 빠른 순, 그다음 우선순위 순으로 한다. 마감일
없는 항목은 뒤에 배치한다. - 완료 항목은 접거나 별도 필터로 확인할 수
있다. - 필터: 전체, 오늘, 미완료, 완료, 마감 임박, 과목, 카테고리 -
마감일은 날짜 기준으로 일관되게 처리한다. - 삭제 및 완료 취소는 데이터에
일관되게 반영한다.

### 6. Focus --- 공부 타이머

-   과목을 선택하고 타이머를 시작한다.
-   TODO 연결은 선택 사항이다.
-   동시에 실행 중인 공부 세션은 사용자당 최대 하나만 허용한다.
-   상태: running / paused / completed (필요하다면 cancelled 추가)
-   시작, 일시정지, 재개, 종료 동작을 제공한다.
-   타이머를 새로고침해도 진행 상태가 사라지지 않아야 한다.
-   브라우저의 setInterval 누적값을 실제 저장 시간의 기준으로 사용하지
    않는다. 시작 시각, 일시정지 시각, 누적 일시정지 구간 또는 이에
    준하는 명시적인 세션 데이터를 사용해 경과 시간을 계산한다.
-   탭이 백그라운드로 이동하거나 기기가 절전 상태가 되어도 경과 시간
    계산이 크게 틀어지지 않아야 한다.
-   종료된 세션은 과목별 공부 시간 및 전체 공부 시간에 정확히 한 번
    반영한다.
-   세션을 수정하거나 잘못 기록된 세션을 삭제하는 기능을 제공한다.
-   자정을 넘긴 세션은 사용자의 시간대 기준으로 날짜별 통계를 나눈다.
-   네트워크 오류가 발생하면 사용자에게 저장 상태를 알려주고, 재시도
    가능한 오류를 조용히 무시하지 않는다.
-   공부 시간 집계는 세션 원본 기록을 기준으로 한다. 전체 시간과 과목별
    시간에 별도의 독립 타이머를 두어 중복 계산하지 않는다.

### 7. Calendar --- 캘린더

-   MVP는 월간 보기부터 구현한다.
-   캘린더에는 TODO 마감일과 독립 일정(시험, 수업, 개인 일정)을 함께
    표시한다.
-   TODO 마감일은 todos 데이터의 due_at에서 파생해 표시한다. 동일한
    TODO를 별도 이벤트로 중복 저장하지 않는다.
-   독립 일정은 별도 calendar_events 테이블에서 관리한다.
-   일정 필드: 제목, 유형, 과목(선택), 시작 시각, 종료 시각(선택),
    메모(선택)
-   날짜 클릭 시 해당 날짜의 TODO와 일정 목록을 표시한다.
-   일정 생성, 수정, 삭제를 제공한다.
-   과목 색상과 일정 유형이 시각적으로 구분되도록 한다.
-   주간/일간 보기, 반복 일정, 외부 캘린더 연동은 MVP 이후 기능이다.

### 8. Analytics --- 학습 분석

MVP에서는 최소한 다음을 제공한다. - 일별 또는 주별 공부 시간 추이 -
과목별 공부 시간과 전체 대비 비중 - 기간별 TODO 완료 개수 및 완료율 -
공부 시간 통계와 TODO 완료율은 서로 다른 지표로 계산한다. - 데이터가
부족할 때는 빈 상태 안내를 제공한다.

### 9. Settings

-   프로필 및 시간대
-   일일 공부 시간 목표
-   주간 시작 요일
-   과목별 주간 목표
-   기본 설정 및 로그아웃

## 데이터 무결성 및 보안

-   모든 테이블에 필요한 외래 키, 인덱스, NOT NULL, CHECK 제약 조건을
    추가한다.
-   사용자별 데이터가 다른 사용자에게 노출되지 않도록 RLS를 적용한다.
-   user_id가 있는 테이블은 인증 사용자와 소유권이 일치하는지 검사한다.
-   categories와 todos의 과목 관계가 일치하는지 서버 또는 DB 레벨에서
    검증한다.
-   사용자당 실행 중인 타이머가 하나만 존재하도록 DB 제약 또는 트랜잭션
    기반 로직으로 보호한다.
-   클라이언트 입력값만 신뢰하지 말고 서버/DB에서 검증한다.
-   모든 시각은 timezone-aware 방식으로 저장하고 표시할 때 사용자
    시간대를 적용한다.
-   TODO와 과목 삭제 정책을 명시하고, 연관 데이터의 고아 레코드를
    방지한다.

## 디자인 가이드

반드시 `design.md` 파일의 지침을 읽고 따른다. 디자인 핵심은 다음과
같다. - Pretendard 폰트 - Toss에서 연상되는 간결하고 정돈된 UI - 밝은
중립 배경과 제한된 포인트 컬러 - 카드형 레이아웃이지만 과도하게 카드가
중첩되지 않도록 한다. - 그림자, 글로우, 과한 그라데이션, 불필요한 장식을
최소화한다. - 얇은 테두리, 여백, 타이포그래피로 정보 위계를 만든다. -
아이콘은 의미가 명확한 선형 아이콘을 사용하고 이모지 남용을 피한다. -
로딩, 빈 상태, 오류, 성공 상태를 모두 디자인한다. - 포커스 표시, 키보드
탐색, 대비, 입력 레이블 등 접근성을 고려한다.

## 구현 순서

다음 순서로 작동 가능한 결과물을 점진적으로 완성한다.

1.  프로젝트 구조 및 현재 상태 확인
2.  디자인 토큰, 공통 레이아웃, 사이드바 구성
3.  인증 및 DB 스키마/RLS 구성
4.  과목·카테고리·TODO CRUD
5.  타이머와 공부 세션 기록
6.  월간 캘린더 및 일정 CRUD
7.  대시보드 통계
8.  Analytics 기본 그래프
9.  오류 처리, 접근성, 보안 검증, 반응형 검수
10. 배포 문서 및 환경 변수 예시 작성

각 단계가 끝날 때마다 타입 검사, 린트, 관련 테스트를 실행하고 오류를
해결한다. 실제로 구현하지 않은 기능을 완성했다고 주장하지 않는다.

## 완료 기준 (Acceptance Criteria)

-   사용자는 회원가입/로그인/로그아웃할 수 있다.
-   사용자 A의 데이터는 사용자 B에게 노출되지 않는다.
-   과목과 과목별 카테고리를 만들고 관리할 수 있다.
-   TODO 생성·수정·완료·삭제가 정상 작동한다.
-   TODO 마감일이 캘린더에 반영된다.
-   독립적인 시험/수업/개인 일정을 등록할 수 있다.
-   타이머 시작·일시정지·재개·종료가 작동한다.
-   새로고침 및 재로그인 이후에도 실행 중 타이머 상태가 복원된다.
-   전체 공부 시간은 공부 세션 원본 데이터에서 집계되며 중복 계산되지
    않는다.
-   자정을 넘긴 세션의 날짜별 통계가 올바르다.
-   대시보드 수치는 실제 저장된 데이터에 기반한다.
-   로딩, 오류, 빈 상태가 구현되어 있다.
-   주요 화면이 PC에서 사용하기 편하고 작은 화면에서도 기본 조작이
    가능하다.
-   `design.md`의 디자인 원칙을 일관되게 적용한다.

## 작업 방식

-   시작 전에 기존 프로젝트 파일과 패키지 구성을 확인한다.
-   기존 기능을 불필요하게 삭제하거나 전체 스택을 임의로 교체하지
    않는다.
-   먼저 구현 계획과 파일 구조를 짧게 제시한 뒤 기능 단위로 구현한다.
-   핵심 사용자 흐름을 우선 구현하고 불필요한 기능을 임의로 추가하지
    않는다.
-   환경 변수가 필요한 경우 `.env.example`을 제공하고 실제 비밀 키는
    커밋하지 않는다.
-   DB 변경 사항은 재현 가능한 migration SQL로 관리한다.
-   실행 방법, 환경 변수, Supabase 설정, 배포 방법을 README에
    문서화한다.


## 배포 및 서버 아키텍처 (필수)

이 프로젝트는 **Vercel + Supabase + GitHub**를 기본 구성으로 사용한다. 별도의 VPS/EC2 서버를 추가하지 않는다. 기존 프로젝트가 다른 스택을 사용 중이면 먼저 현재 상태를 확인하고, 변경 필요성을 설명한다.

- **Vercel**: Next.js 웹사이트 호스팅, 자동 배포, 필요한 서버 측 API/Server Actions/Route Handlers 실행
- **Supabase Auth**: 회원가입, 로그인, 세션
- **Supabase PostgreSQL**: 과목, 카테고리, TODO, 일정, 공부 세션, 사용자 설정 저장
- **Supabase Row Level Security (RLS)**: 사용자별 데이터 접근 통제
- **GitHub**: 소스 코드와 migration 관리, Vercel 배포 연동

### 배포 요구사항
1. GitHub 저장소와 Vercel 프로젝트를 연결한다.
2. 로컬 개발과 Vercel 배포에 필요한 환경 변수 목록을 `.env.example`에 작성한다. 실제 비밀 키는 저장소에 커밋하지 않는다.
3. Supabase 스키마 변경은 `supabase/migrations/` 아래 재현 가능한 SQL migration으로 관리한다.
4. 브라우저에서 필요한 Supabase anon/publishable key만 사용하고, service role key는 서버 환경 변수에만 둔다.
5. 사용자별 데이터가 분리되도록 RLS 정책을 적용하고 테스트한다.
6. Vercel Hobby 무료 플랜을 우선 가정하되, 플랜별 사용량·기능 제한은 배포 시점에 확인하도록 문서화한다. 무료 사용량을 무제한이라고 가정하지 않는다.
7. Supabase 무료 플랜의 비활성 프로젝트 일시정지 등 제한을 README에 안내한다.
8. Vercel Functions는 요청 기반 서버 기능에 사용한다. 타이머를 위해 상시 실행 서버를 만들지 않는다.
9. 타이머는 클라이언트에서 시작 시각과 저장된 누적 시간으로 경과 시간을 표시하고, 세션 상태를 Supabase에 저장한다. 전체 공부 시간과 과목별 시간은 같은 세션 기록에서 집계한다.
10. 프로젝트가 실제로 배포되었다고 주장하지 말고, 배포 전 필요한 계정 연결 및 환경 변수 설정을 명확히 안내한다.

### 환경 변수
프로젝트 구성에 맞춰 `.env.example`을 만든다. 예시는 다음과 같으며, 실제 사용 중인 Supabase SDK/API 방식에 맞춰 변수명을 확인한다.

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY` 또는 해당 SDK가 권장하는 publishable key 변수
- 서버 전용 비밀 키가 필요한 경우에만 별도 서버 환경 변수로 추가하고 `NEXT_PUBLIC_` 접두사를 붙이지 않는다.

### 권장 배포 순서
1. GitHub에 코드를 푸시한다.
2. Supabase 프로젝트를 만들고 DB migration을 적용한다.
3. Supabase Auth URL 및 redirect URL을 로컬/프로덕션 주소에 맞게 설정한다.
4. Vercel에서 GitHub 저장소를 가져온다.
5. Vercel 환경 변수에 Supabase URL과 공개 클라이언트 키를 등록한다.
6. Preview 배포에서 로그인, CRUD, 타이머, RLS를 확인한다.
7. Production 배포 후 핵심 사용자 흐름을 다시 점검한다.
